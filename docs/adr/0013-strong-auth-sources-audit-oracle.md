# ADR-0013 — Strong-auth events: boot (LUKS), root attestation, kernel audit oracle

Status: accepted; oracle opt-in.

## Context
The lock-screen password runs inside Quickshell's uid-1000 child and its lane is rewritten by `omarchy-apply-lock`: no trustworthy "password succeeded" message can reach the daemon. Yet lockout reset and freshness need a strong anchor. Verified: `pam_unix` in that child delegates to setuid `unix_chkpwd`, which logs `AUDIT_USER_AUTH ... res=success` when `ruid != 0`; emitting such records needs `CAP_AUDIT_WRITE`; journald marks kernel records `_TRANSPORT=audit`. Kernel auditing is currently off here (`systemd-journald-audit.socket` disabled). `sudo` caches credentials, so "sudo asked for a password" is not a reliable anchor.

## Decision
SAE sources, in order of availability: (a) new `boot_id` when `boot_is_strong_auth=true` (setup runs `cryptsetup luksDump` as root; `true` only for passphrase-only LUKS without tpm2/fido2/pkcs11 tokens; `doctor` re-checks); (b) `sudo nirlockctl attest|reset-lockout|enroll|delete`, which performs its own `pam_authenticate` of the target user via `pam_start_confdir("nirlock-admin", user, conv, "/usr/lib/nirlock/pam.d")` (as root; `pam_unix` reads shadow directly, no `unix_chkpwd`, no audit record). The stack is exactly `auth [success=done default=die] pam_unix.so` / `auth required pam_deny.so` — no `system-auth` (its `auth optional pam_permit.so` fails open), no `pam_faillock` (root attestation attempts must never lock the user's password), no `nullok` — and the conversation answers only `PAM_PROMPT_ECHO_OFF`, returning `PAM_CONV_ERR` on any other message style (DESIGN §4.4, ADR-0012). Expected codes: correct 0, wrong 7, unknown user ≠ 0, missing file → `other` → 7. (c) optional audit oracle: `systemd-journald-audit.socket` enabled with consent (plus a journald drop-in `Audit=yes` if M5 shows the socket alone does not start kernel auditing); the daemon (group `systemd-journal`) consumes records matching `_TRANSPORT=audit`, `_AUDIT_TYPE=1100`, `_AUDIT_FIELD_OP=PAM:unix_chkpwd`, `_AUDIT_FIELD_ACCT=<user>`, `_AUDIT_FIELD_UID=<uid>`, `_AUDIT_FIELD_RES=success`, with `_BOOT_ID` = current boot and monotonic timestamp later than the last failure and than a watermark set to "now" whenever the cursor is unknown. **Not `_UID`**: journald does not attach `_UID` to kernel-originated audit records; the audited process's uid is in `_AUDIT_FIELD_UID` (and `_AUDIT_LOGINUID`). `nirlockctl doctor --oracle` asks for a real password unlock and checks that a matching record appeared. Face accepts are never SAEs.

## Alternatives
Trusting a wrapper message (forgeable); hooking `/etc/pam.d/omarchy-lock-password` (rewritten weekly, uid-1000 host anyway); a `pam_exec` marker in `/etc/pam.d/sudo` (touches the sudo stack; v1.1 option); a setuid helper of our own (TCB growth).

## Consequences
With the oracle on, typing the password at the lock screen clears a hard lockout and refreshes the 24 h window (Windows Hello semantics). Without it, freshness is 72 h and clearing needs a reboot or a root command. The oracle replay hole is closed by the watermark. Whether enabling the audit socket at runtime starts kernel auditing immediately is verified in M5.
